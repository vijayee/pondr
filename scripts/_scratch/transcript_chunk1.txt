            self.utility_decay_rate *= 0.3

## The Problem: Unbounded Positive Feedback

```plaintext
User asks about WAL config → retrieved → decay rate drops
User asks again tomorrow → retrieved again → decay rate drops further
User asks a third time → retrieved again → even more persistent
...
After 20 retrievals: edge is effectively immortal

But WHY is the user asking 20 times?
- Maybe WAL config is genuinely important (should be persistent)
- Maybe the answer is confusing and the user keeps not understanding (should NOT be persistent — the memory is failing its purpose)
- Maybe the user is annoyed and keeps coming back to fix it (should be persistent but the user might want it gone)
```

The system can't distinguish these from retrieval count alone. It needs additional signals.

## The Fix: Self-Limiting Reinforcement

Four mechanisms that together prevent immortal memories:

### 1. Diminishing Returns on Retrieval Boost

Each retrieval provides less persistence boost than the previous one. The curve approaches a floor asymptotically:

```python
def on_retrieve(self, retrieval_strength: float = 1.0):
    self.access_count += 1
    self.last_accessed = now()
    self.reconsolidation_count += 1
    
    # ── Diminishing returns ──
    # First retrieval: 5% reduction in decay rate
    # 5th retrieval:  ~2% reduction
    # 20th retrieval: ~0.5% reduction
    # Approaches but never reaches zero decay
    base_boost = 0.05 * retrieval_strength
    diminishing_factor = 1.0 / (1.0 + 0.3 * self.reconsolidation_count)
    effective_boost = base_boost * diminishing_factor
    
    self.utility_decay_rate = max(
        0.001,  # absolute floor: 0.1% per day minimum decay
        self.utility_decay_rate * (1 - effective_boost)
    )
```

The decay rate never reaches zero. Even the most-accessed edge decays at 0.1% per day — it would take ~2 years to decay to 50% utility. Long, but not immortal.

### 2. Retrieval Saturation Detection

If the same edge is retrieved too many times in a short window, the system stops boosting and may even increase decay:

```python
def on_retrieve(self, retrieval_strength: float = 1.0):
    now_time = now()
    
    # ── Saturation check ──
    # How many times has this edge been retrieved in the last 24 hours?
    recent_retrievals = [
        t for t in self.retrieval_timestamps
        if (now_time - t).total_seconds() < 86400
    ]
    
    if len(recent_retrievals) > SATURATION_THRESHOLD:  # e.g., 5 times in 24 hours
        # Saturation detected. The user keeps asking about this.
        # Don't boost. Possibly increase decay slightly.
        # The system is failing to provide a satisfactory answer,
        # or the user is stuck in a loop. Persisting this memory
        # harder is counterproductive.
        self.utility_decay_rate = min(
            0.05,  # cap: 5% per day max
            self.utility_decay_rate * 1.02  # slight increase
        )
        self.saturation_flags += 1
        return  # Skip the normal boost
    
    # Normal path: apply diminishing returns boost
    self.retrieval_timestamps.append(now_time)
    # ... rest of normal boost logic
```

This prevents the "frustration loop" — the user keeps asking because the answer isn't sticking, and the system keeps reinforcing the memory because the user keeps asking. The saturation threshold breaks the cycle.

### 4. Boost Decay Over Time

The persistence boost from a retrieval itself decays. A retrieval last month matters less than a retrieval yesterday:

```python
def compute_effective_decay_rate(self):
    """
    The decay rate is not a single stored value.
    It's computed from retrieval history, weighted by recency.
    """
    now_time = now()
    
    # Base decay rate
    effective_rate = self.base_decay_rate  # 0.01 per day
    
    # Each retrieval provides a temporary boost that decays
    for retrieval_time in self.retrieval_timestamps[-50:]:  # last 50 retrievals
        days_ago = (now_time - retrieval_time).days
        
        # Boost from this retrieval decays with time
        boost = 0.05 * (0.9 ** days_ago)  # half-life of ~7 days
        
        # Apply diminishing returns based on how many retrievals came before it
        retrieval_index = self.retrieval_timestamps.index(retrieval_time)
        diminishing = 1.0 / (1.0 + 0.3 * retrieval_index)
        
        effective_rate *= (1 - boost * diminishing)
    
    return max(0.001, effective_rate)
```

This means: if the user asks about WAL config 20 times in one week, the decay rate drops sharply. But if they stop asking, the boost fades over the following weeks, and the decay rate gradually rises back toward baseline. The memory is persistent while it's actively used, not permanently.

# Ponder Engine: A Hippocampal Memory Architecture for AI Agents

**A brain-inspired alternative to the context window that separates knowledge from processing, enables an artificial subconscious, and makes domain expertise a transferrable, composable resource.**

**Technical Architecture Proposal — v2.0, July 2026**

---

## Executive Summary

Current AI agents rely on **context windows** — fixed-size text buffers that concatenate conversation history and feed it to a language model. This is a von Neumann architecture solution to a biological problem: separate storage from processing, copy data between them, truncate when the buffer overflows. The brain never evolved this assumption. It stores patterns in the same neurons that process them, and "retrieval" is reactivation of those neurons via sparse hippocampal pointers.

We propose a **ponder engine** — a hippocampal memory architecture that replaces the context window with a brain-inspired alternative. The system encodes conversation, documents, code, and multimedia into structured triples stored in a graph-based hippocampal index over a distributed content store. Working memory is the set of currently activated patterns rather than a fixed text buffer. Retrieval is pattern completion via graph traversal. Consolidation occurs during offline "dream state" passes via a graph neural network. Forgetting is managed versioning, not destructive truncation.

Beneath conscious awareness, a **subconscious routing system** continuously decides which domain to query, which retrieval pathway to use, what model size is needed, and whether conscious deliberation is even required. This router learns from every interaction, becoming personalized over time.

The architecture is built on **WaveDB** — an existing hierarchical key-value database with MVCC concurrency, a Graph layer with Gremlin-style traversal, and production Python bindings — combined with small, specialized models for extraction, reasoning, and consolidation. The entire system runs on consumer hardware. Total training cost: ~$120. Total inference cost: $0.

---

## 1. Problem Statement

### 1.1 The Context Window Is the Wrong Abstraction

Every major AI assistant operates on the same fundamental model:

```plaintext
User query → [entire conversation history loaded into context window]
              → LLM processes via self-attention → response
```

This has three structural problems:

| Problem | Consequence |
|---|---|
| **Fixed capacity** | When conversation exceeds the token limit, information is permanently lost via truncation, summarization, or sliding windows — all lossy hacks |
| **O(n²) attention** | Every token attends to every other token. Computational cost grows quadratically with conversation length |
| **No native memory** | The model has no persistent memory between sessions. RAG adds an explicit retrieval step, but it's bolted on, not integrated |

### 1.2 The Brain Does It Differently

The brain does not "load" memories into a buffer. It stores a **sparse index** in the hippocampus — compressed pointers to the neocortical neurons that, when reactivated together, reconstruct the memory. This is **hippocampal indexing theory** (Teyler & DiScenna, 1986).

The retrieval process:

1. **A cue arrives** — a partial input (a face, a smell, a question)
2. **Pattern completion in CA3** — the hippocampal subfield CA3 is a recurrent autoassociative network. It takes the partial cue and fills in the missing components, reconstructing the full hippocampal index in ~100–200 milliseconds
3. **Neocortical reactivation** — the completed hippocampal index sends signals back to the neocortical sites it points to. The memory is **reconstructed**, not retrieved
4. **The reconstruction IS the short-term access** — there is no separate "working memory copy." Working memory is simply the subset of long-term memory currently activated by attention (the **embedded-processes model**, Cowan 1999, 2005)

The brain also has **complementary learning systems**: the hippocampus learns fast and separates patterns, while the neocortex learns slow and extracts statistical regularities. During sleep, the hippocampus replays memories to gradually train the neocortex without catastrophic interference. And beneath conscious awareness, the **basal ganglia** continuously route between processing pathways — a subconscious gating system that learns which cognitive mode to engage based on context.

### 1.3 What We're Building

A memory architecture for AI agents that mirrors this design, with three key innovations beyond biological mapping:

1. **A learned subconscious router** that decides which domain to query, which pathway to use, and what model size is needed — before any model generates a token
2. **Domain knowledge as transferrable graphs** — expertise that can be exported, imported, and composed without retraining any model
3. **A bidirectional interface** that lets any LLM consume curated context and write back memory commands

| Brain Component | Our Implementation |
|---|---|
| Neocortical store (distributed, slow-learning) | WaveDB HBTrie — hierarchical key-value store with MVCC |
| Hippocampal index (sparse, fast-learning) | WaveDB Graph layer — triple store with SPO/POS/OSP indexes |
| CA3 pattern completion | Graph traversal (Gremlin-style) from partial cues |
| Sharp-wave ripple replay | GNN-driven consolidation during offline "dream state" |
| Working memory | SSM (Mamba) continuous hidden state + activated graph nodes |
| Basal ganglia routing | JEPA gate — learned subconscious router |
| Dopamine/salience modulation | JEPA predictor + retrieval-weighted persistence |
| Reality monitoring | Bonsai (ternary 8B model) waking during anomalies |
| Systems consolidation | Morphism formation + subgraph abstraction into semantic memories |
| Procedural memory (basal ganglia/cerebellum) | Stored processes with delegation rules |

## 3. Component Justifications

### 3.1 WaveDB Graph Layer → Hippocampal Index

**Why not a vector database?** Vector similarity answers "what's similar to this?" but not "what did Alice say about databases last week?" or "what happened after we implemented morphisms?" The graph stores **discrete, symbolic relationships** — entity presence, topic classification, affective state, temporal order, decisions, contradictions, citations. These are different in kind from embedding similarity and answer different questions.

**Why WaveDB specifically?** WaveDB provides a triple store with SPO/POS/OSP indexes, Gremlin-style traversal, cost-based query optimization, and morphisms (reusable query fragments). The morphism system maps directly to **systems consolidation** — frequently traversed paths become single named pathways, analogous to how the neocortex learns direct connections after repeated hippocampal replay.

**Key design decision:** The graph stores **structure** (who, what, when, how felt, in what order). The HBTrie stores **content** (the actual words, code, media). The vector index stores **similarity**. Each answers different questions, and together they form a memory system no single component could provide.

### 3.2 WaveDB HBTrie → Neocortical Store

**Why hierarchical key-value?** The HBTrie's hierarchical paths (`episodes/ep_47/summary`, `entities/alice/properties/name`, `code/auth.py@v3/content`) map naturally to distributed cortical representations. Each level is a "cortical region" — same underlying storage, different organizational principles.

**Why MVCC?** Multi-Version Concurrency Control provides snapshot isolation — every read sees a consistent version. This maps to **state-dependent memory**: the same memory can have different "versions" depending on when you access it. Combined with edge validity windows in the Graph layer, this enables temporal queries ("what did I know at time T?") without losing historical versions.

### 3.3 GLiNER-Decoder → Open Entity Discovery

**Why not just use a predefined schema?** A static schema is a filter — it tells the system what to see, which means it also tells it what to ignore. The brain discovers categories through experience. GLiNER-Decoder (Knowledgator, 205M parameters) uses a small generative decoder to **invent labels** for discovered entities rather than matching against a predefined list. Given `labels=["label"]`, it produces spans with freely generated type names.

**Why it matters:** The system discovers that this user talks about `deployment`, `testing`, and `documentation` — categories no one predicted. These discovered labels are clustered, canonicalized, and promoted to the stable schema over time. The schema is alive.

### 3.4 GLiNER2 → Stable Extraction

**Why two GLiNER variants?** GLiNER-Decoder is flexible but inconsistent — the same entity might be labeled `"configuration option"` in one conversation and `"setting"` in another. GLiNER2 (Fastino, 205M parameters) extracts against a stable, evolved schema with consistent labels. It's faster and more reliable for categories that have been promoted from discovery.

**Why 205M parameters?** A 459M GLiNER encoder outperformed ChatGPT (~175B) on named entity recognition benchmarks. For extraction tasks, specialized small models beat generalist large models. GLiNER2 runs on CPU, costs nothing per inference, and produces structured output in a single forward pass.

### 3.5 Bonsai → Relation Reasoning, Query Planning, Verification

**Why an 8B ternary model?** Three distinct roles require reasoning beyond what GLiNER can do:

1. **Relation extraction:** GLiNER finds entities. Bonsai determines how they relate — "Alice explained DEBOUNCED," "User decided to use HBTrie," "This contradicts the earlier decision." This requires understanding semantic content, not just spotting named entities.

2. **Query planning:** Converting "What was I frustrated about last week?" into `{tones: ["frustrated"], temporal_filter: "last_week", entity_mode: "union"}` requires reasoning about query intent. GLiNER can extract entities from the prompt, but it can't determine that "Alice and I decided" means entity_mode should be "union" (episodes involving Alice) rather than "intersection" (episodes containing both Alice AND the user).

3. **Reality monitoring:** During consolidation, Bonsai wakes to verify GNN-flagged anomalies. The ternary weights {-1, 0, +1} map to inhibitory/excitatory/absent synapses — the model can actively suppress incoherent reconstructions, not just fail to excite them.

**Why ternary?** The 8B ternary model occupies ~2.15 GB — it fits on an RTX 5060 Ti (16 GB) alongside the SSM and JEPA. Ternary weights also map to biological synapse states: potentiated (+1), depressed (-1), or silent/absent (0).

### 3.6 JEPA-Gated SSM → Unified Cognitive Primitive

**Why a shared backbone?** The previous architecture treated the Mamba SSM, JEPA Predictor, and Gate as separate models with separate purposes. This had three consequences: proliferation of models (each new cognitive function required a new model), no unified dynamics (components were independent when they should be aspects of a single primitive), and missing cognitive functions (no disturbance detection, no prospective memory, no developmental staging).

The JEPA-gated SSM primitive solves this through a critical distinction: **shared weights, separate states.** The SSM and JEPA weights are loaded once in GPU memory (~480M parameters, ~0.90 GB). Every cognitive function is an instance with its own state vector (512 floats, ~2 KB), its own gate (~500K parameters), and its own input/output projections (~100K parameters). Adding a new cognitive function costs ~1M parameters, not ~500M.

**Why this doesn't collapse:** A single state vector cannot simultaneously represent retrieval gating, working memory maintenance, uncertainty detection, aspiration, and self-modeling. These are different kinds of information with different temporal dynamics. The architecture prevents collapse through separate state spaces (each instance has its own 512-dimensional vector), input/output projections (learned lenses that map instance-specific inputs into the shared representational space), and instance-specific gates (each learns its own inhibit/excite policy).

**Biological mapping:** This maps onto the canonical cortical microcircuit — the same cell types, laminar structure, and local connectivity repeated across the entire neocortex. What differs between regions is input sources, output targets, and inhibitory interneuron composition. The circuit is the same. The configuration makes it different.

### 3.7 Retrieval Gate → Subconscious Router

**Why learned, not rule-based?** The decision of which domain to query, which pathway to use, and what model size is needed depends on nuanced factors: how recently was this entity discussed? How confident is the SSM about this topic? Is this a follow-up question or a topic shift? Is this pattern similar to past queries that required delegation? A learned gate learns these patterns from experience.

**What it predicts (before any model generates a token):**
- **Domain routing:** Which domain graph(s) to query — database, robotics, economics, coding, personal
- **Pathway selection:** ssm_direct | graph_retrieve | process_exec | tool_plan | conscious_deliberation
- **Meta-skill prediction:** What cognitive capabilities are needed — factual_recall, basic_synthesis, pattern_recognition, creative_synthesis, security_analysis
- **Model sizing:** 1B | 3B | 8B | 70B | 175B
- **Deliberation gating:** Can the subconscious handle this, or does System 2 need to engage?

**How it learns:** Every routing decision produces an outcome. Did the user accept the response? Did the model have to delegate unexpectedly? Was expansion needed? These outcomes feed back as reinforcement signals. Successful routes are reinforced. Routes that required unexpected delegation are penalized. Routes that used a larger model than necessary get an efficiency penalty. Over time, the gate becomes personalized — it learns your domains, your patterns, your habits.

### 3.8 Working Memory → Continuous Awareness

**Why not a transformer?** Transformers have O(n²) attention — the thing we're trying to escape. State Space Models (Mamba) maintain a continuous hidden state that evolves with each input. There is no fixed context window. Old information decays gracefully rather than being truncated. The state dimension is constant, but the information it represents expands and contracts dynamically.

**Why it's working memory:** The SSM state IS the currently activated subset of everything the system knows. When the retrieval gate determines the state is sufficient, no graph retrieval is needed — the SSM state alone generates the response. When the gate detects low confidence, it triggers graph retrieval and the retrieved content is injected into the SSM state as embeddings, not text.

### 3.9 Uncertainty Detector → Knowing When You Don't Know

**Why it matters:** Without uncertainty detection, the system either confabulates (generates from insufficient context) or retrieves unnecessarily (wastes computation on queries the SSM state already covers). The Uncertainty Detector flags three conditions:

1. **Routing uncertainty:** JEPA confidence is below threshold for the routed domain
2. **Novel entities:** Retrieved context contains entities not in the ontology
3. **Unresolved contradictions:** Multiple sources contradict without resolution

These flags feed the EXPAND mechanism (load more detail from HBTrie) and the delegation ladder (route to a larger model). The detector learns its thresholds from experience — during gestational training, the Oracle provides feedback on when the system should have known it didn't know.

### 3.10 Aspirational Model → Three Temporal Modes

**Why three modes?** Wanting operates in all three temporal directions. The same dopaminergic signal that gates encoding also maintains goal representations in working memory (prospective intention) and tags memories for replay priority during consolidation. The Aspirational Model reflects this unity:

- **Present (encoding gate):** Modulates encoding strength based on aspirational match. "I'm curious about this → encode strongly." Implemented through JEPA salience scoring.
- **Future (prospective memory):** Sets triggers that fire when conditions are met. "Alert me when you encounter information about X." The system checks pending triggers before each retrieval loop.
- **Past (retrieval-weighted persistence):** Every retrieval boosts the edge's long-term survival probability. The more the user asks, the harder it is to forget — with self-limiting mechanisms to prevent immortal memories.

### 3.11 Self-Model → Knowledge Boundary Estimation

**Why learned thresholds?** The system needs to know when to say "I don't know." Hardcoded thresholds ("if graph density < 0.3, admit gap") fail because different domains have different knowledge densities. A sparse but complete domain (3 episodes about a niche topic) should produce confident answers. A dense but incomplete domain (100 episodes but missing the specific fact) should not. The Self-Model learns these boundaries from Oracle feedback during gestational training.

### 3.12 GNN Consolidator → Dream State Processing

**Why a graph neural network?** The consolidation tasks — salience scoring, subgraph summarization, link prediction, anomaly detection, ontology refinement — all require reasoning about **graph structure**, not just node features. A node's importance depends on its position in the graph (bridge, hub, peripheral), not just its content. GNNs are the standard tool for this class of problem.

**Why offline?** Consolidation is computationally intensive and benefits from seeing the full graph. Running it during the dream state (offline, periodic) mirrors the brain's sharp-wave ripple replay during sleep. The GNN identifies clusters for abstraction, predicts missing edges, detects anomalies, and refines the ontology — then Bonsai verifies the high-stakes decisions.

**Why static first, temporal later?** The initial GNN is a stateless function: `consolidate(graph) → actions`. After collecting data on failure modes (cluster flapping, prediction miscalibration, false positive anomalies, ontology oscillation), we add SSM-augmented instances that remember past decisions. This prevents premature optimization — we build temporal continuity only for the failure modes that actually occur.

### 3.13 Forgetting System → Self-Limiting Persistence

**Why not flat decay?** Flat utility score decay treats all edges identically. But edges that are repeatedly retrieved should persist longer — not indefinitely, but proportionally to demonstrated importance. The forgetting system combines four mechanisms:

1. **Retrieval-weighted persistence:** Each retrieval reduces the edge's decay rate. Strong matches (direct entity+topic+tone match) reduce it more than weak matches (ontology expansion). Diminishing returns prevent immortal memories — the 20th retrieval provides far less boost than the 1st.

2. **Saturation detection:** If the same edge is retrieved more than N times in 24 hours, the system stops boosting and may slightly increase decay. This breaks the "frustration loop" — the user keeps asking because the answer isn't sticking, and the system keeps reinforcing because the user keeps asking.

3. **LLM-mediated importance signal:** The LLM embeds signals in its response — `[IMPORTANT]`, `[ROUTINE]`, `[FRUSTRATION]`, `[CORRECTION]`. These modulate the persistence boost. A frustration signal prevents reinforcement. A correction signal may increase decay on the old fact.

4. **Boost decay:** The persistence boost from a retrieval itself decays with a ~7-day half-life. A retrieval last month matters less than a retrieval yesterday. If the user stops asking, the boost fades and the edge returns to baseline decay.

**Reconsolidation counting:** Edges track how many times they've been retrieved. Three retrievals across 15+ days triggers late-phase LTP — a 70% reduction in decay rate on top of accumulated boosts. This is the architectural equivalent of the transition from hippocampal-dependent to neocortical-independent memory.

### 3.14 Process Executor → Procedural Memory

**Why stored processes?** When the system observes the user performing the same multi-step task three times, it proposes a stored process. The fourth time, the user says "review this" and the system executes the process automatically, delegating individual steps to larger models when they exceed the current model's capability.

Processes are stored in the same graph as everything else — they're just subgraphs with a specific shape. Each step specifies what tool to use, what model size is needed, and what to do on failure (delegate, skip, ask_user, abort). Meta-processes — strategy templates with decision points rather than fixed steps — guide the model's reasoning when no concrete process matches.

### 3.15 Delegation Ladder → Capability-Appropriate Intelligence

**Why delegate?** A 1B model can summarize. A 3B model can synthesize. An 8B model can reason. A 70B model can design. A 175B model can create. The delegation ladder routes each step of a process to the smallest model that can handle it, escalating only when necessary. The user never knows a larger model was invoked.

The Retrieval Gate learns which model size is needed for which patterns. Over time, it routes directly to the right size without trial and error. Most real-world queries (80%) are handled by the 1-3B models. The 70B+ models sit idle until genuinely needed.

### 3.16 Oracle (DeepSeek) → Gestational Training

**Why an Oracle?** Several components require training data that doesn't exist in public datasets: query planning pairs, relation extraction from conversational text, salience labels on memory graphs, gate training examples. The Oracle generates this data during a gestational training phase.

**Why not permanent?** The Oracle is expensive per call. It generates 5,000-10,000 training examples per component during initial training, then the components operate independently. The Oracle is only invoked again if the system encounters genuinely novel situations that the fine-tuned models can't handle. The Developmental Tracker gates this — components graduate from INFANT (Oracle provides all signal) to CHILD (Oracle critiques decisions) to ADOLESCENT (self-regulating) to ADULT (independent).

## 4. Information Flow

### 4.1 Encoding Flow (Every Conversation Turn)

```plaintext
1. Raw conversation text enters the system

2. GLiNER-Decoder performs open discovery:
   "WAL config" → "technical concept"
   "DEBOUNCED" → "configuration option"
   "confusing" → "sentiment"
   "go with DEBOUNCED" → "decision"
   → Raw entity spans with invented type labels

3. GLiNER2 performs stable extraction against the evolved schema:
   entities: ["Alice", "WaveDB"]
   topics: ["configuration"]
   tones: ["frustrated", "curious"]
   decisions: ["use_debounced"]
   → Structured, consistent labels

4. Discovered labels are buffered. Labels appearing >10 times
   are clustered, canonicalized, and promoted to the stable schema.
   "configuration option" + "setting" + "parameter" → "configuration"

5. Bonsai extracts relations:
   (User, expresses, frustrated)
   (User, questions, WAL_sync_modes)
   (Alice, explains, WAL_sync_modes)
   (User, decides, use_debounced)
   (conversation, concerns, configuration)
   (conversation, involves, Alice)

6. Aspirational Model (present mode) scores encoding strength:
   salience = 0.65 (moderate — contains a decision but routine topic)
   → Encode at baseline strength

7. Storage:
   Graph layer: insert all triples as edges
   HBTrie: store summary, full text, timestamp
   Vector index: store embedding of summary for semantic search

8. Process Observer checks for repeated patterns:
   "User asked about config → assistant explained → user decided"
   Seen 3 times? → Propose stored process
```

### 4.2 Retrieval Flow (On User Prompt)

```plaintext
1. User prompt: "What was I frustrated about last week?"

2. Aspirational Model (future mode) checks pending triggers:
   Any prospective memories matching this context?
   → None found. Continue.

3. Retrieval Gate (subconscious router) evaluates:
   - "frustrated" tone not in recent SSM state → low confidence
   - "last week" temporal scope → SSM state only covers recent turns
   - Domain: database (confidence 0.89)
   - Pathway: graph_retrieve
   - Model size: 3B (factual_recall + basic_synthesis)
   - Deliberation: NOT NEEDED
   → TRIGGER GRAPH RETRIEVAL

4. Bonsai plans the query:
   {
     entities: [],
     topics: [],
     tones: ["frustrated"],
     entity_mode: "union",
     temporal_filter: "last_week",
     limit: 5
   }

5. Ontology Expander expands the query:
   "frustrated" → Frustrated (subclass of AffectiveTone)
   → Also match episodes with tone "Frustrated"

6. Graph traversal (pattern completion):
   - Find all episodes with tone "frustrated" (union)
   - Filter by timestamp > 7 days ago
   - Score by: tone match count + recency + retrieval history
   - Return top 5

7. HBTrie load (neocortical reactivation):
   For each result episode ID:
     load summary, full_text, timestamp from HBTrie

8. Working memory = activated graph nodes + HBTrie values + SSM state

9. Uncertainty Detector checks:
   - Routing confidence: 0.89 → OK
   - Novel entities in results: none → OK
   - Unresolved contradictions: none → OK
   → No flags. Proceed.

10. Response generation from working memory

11. Retrieval-weighted persistence:
    For each edge traversed in retrieval:
      on_retrieve(retrieval_strength, llm_signal)
      → Decay rate reduced (diminishing returns)
      → Saturation check passed
      → Reconsolidation count incremented
```

### 4.3 Consolidation Flow (Dream State — Periodic)

```
1. GNN scores all nodes/edges by structural salience:
   - ep_001: 0.92 (anchor episode, foundational decision)
   - ep_005: 0.30 (routine, redundant paths exist)
   - edge ep_003_has_entity_Bob: 0.80 (only connection for Bob)
   - Salience incorporates: access_count, reconsolidation_count, ltp_phase

2. GNN detects subgraphs ready for abstraction:
   Cluster: [ep_001, ep_002, ep_003, ep_004]
   → Abstract to: "WaveDB initial development (June 20-23)"
   → Store semantic memory in HBTrie
   → Link semantic memory to source episodes
   → Mark source episodes as "abstracted" (still retrievable)

3. GNN predicts missing edges:
   (Postgres, related_to, performance) confidence 0.82
   → Auto-accept (confidence > 0.8)
   (ep_006, caused_by, ep_005) confidence 0.75
   → Propose for Bonsai verification (confidence 0.5-0.8)

4. GNN detects anomalies:
   - MISSING_TEMPORAL: ep_007 follows ep_004, but ep_005-006 also follow ep_004
     → Wake Bonsai: "Are these parallel threads?"
   - DUPLICATE_DECISION: use_hbtrie (ep_001) and use_wavedb_over_postgres (ep_003)
     → Wake Bonsai: "Are these the same decision?"

5. Bonsai verifies anomalies:
   - Temporal branch: "Legitimate parallel threads. No change needed."
   - Duplicate decision: "Distinct decisions. Add 'reinforces' edge."

6. Forgetting pass:
   - Compute effective decay rate for each edge (incorporates retrieval history)
   - Edges with utility_score < 0.1 and state="current" → state="archived"
   - Superseded edges older than 90 days → compress to summary, archive
   - Boost decay: old retrieval boosts fade (half-life ~7 days)
   - Ontology categories not seen in 30+ days → deprecate

7. SSM replay:
   - Replay high-salience consolidated memories through SSM
   - Strengthens neocortical (SSM weight) representations

8. Developmental Tracker evaluates:
   - Extraction F1 > 0.85? → Graduate from INFANT to CHILD
   - Retrieval recall > 0.80? → Graduate from INFANT to CHILD
   - Gate decisions match Oracle > 0.75? → Graduate from INFANT to CHILD
```

### 4.4 Forgetting Flow (Continuous + Periodic)

```
1. RETRIEVAL-WEIGHTED PERSISTENCE (on every retrieval):
   - Diminishing returns: each retrieval boosts less than the previous
   - Saturation detection: >N retrievals in 24 hours → stop boosting
   - LLM-mediated signal: [IMPORTANT] → stronger boost, [FRUSTRATION] → no boost
   - Boost decay: old retrieval boosts fade with ~7-day half-life
   - Absolute floor: decay rate never reaches zero (minimum 0.1%/day)

2. RECONSOLIDATION COUNTING (on every retrieval):
   - Track reconsolidation_count and consolidation_window_start
   - 3 retrievals across 15+ days → late-phase LTP
   - Late-phase LTP: additional 70% reduction in decay rate

3. ACTIVE FORGETTING (user-triggered):
   - User: "Forget what I said about Postgres"
   - Edge state → "deprecated"
   - validity_end → now()
   - Edge still exists, not returned by default queries
   - Retrievable via historical query: "what did I used to think?"

4. RECONSOLIDATION (on contradiction):
   - New fact contradicts old fact
   - Old fact: state → "superseded", validity_end → now()
   - New fact: state → "current", validity_start → now()
   - Link: new_fact supersedes old_fact, new_fact contradicts old_fact
   - Both versions preserved. Default queries return current only.

5. PRUNING (periodic consolidation):
   - Archived edges older than 365 days → deep archive
   - Superseded edges → compressed to summary in HBTrie
   - Nothing is ever truly deleted. Storage is cheap.
```

## 9. Key Design Decisions & Tradeoffs

### 9.1 Why Not a Single Large Model?

A single large model that does extraction, retrieval, and generation would be simpler. But:

- **Cost:** Running a 70B+ model for every conversation turn is expensive. GLiNER2 runs on CPU and costs nothing per inference. The delegation ladder only invokes large models when needed.
- **Specialization:** A 459M GLiNER encoder outperformed ChatGPT (~175B) on NER. Specialized small models beat generalist large models on their specific tasks.
- **Interpretability:** When retrieval fails, you can inspect the graph traversal to see why. A large model's retrieval is a black box.
- **Updateability:** You can fine-tune GLiNER2 on new entity types without retraining the entire system.

### 9.2 Why Not Pure Vector Search?

Vector search answers "what's similar to this embedding?" It doesn't answer:
- "What did Alice say about databases?" (entity + topic constraint)
- "What happened after we implemented morphisms?" (temporal chain)
- "What decisions did we make and why?" (relation type constraint)
- "What was I frustrated about?" (affective state constraint)

The graph stores these as discrete, queryable relationships. Vector search is complementary — it handles the "similar to this" queries that the graph can't.

### 9.3 Why Offline Consolidation?

Running the GNN on every conversation turn would add latency and computational cost. The brain doesn't consolidate in real-time either — it replays memories during sleep. The offline "dream state" pass allows the GNN to see the full graph, make global decisions about salience and abstraction, and not compete with real-time inference for GPU resources.

### 9.4 Why Never Delete?

Storage is cheap. The value of being able to answer "what did I used to think?" or "what changed and when?" outweighs the cost of keeping superseded edges. MVCC in WaveDB already versions every write. Edge validity windows add temporal semantics. The combination gives you current, historical, and change views without destructive operations.

### 9.5 Why Shared Weights, Separate States?

A single SSM state vector cannot simultaneously represent retrieval gating, working memory maintenance, uncertainty detection, aspiration, and self-modeling. These are different kinds of information with different temporal dynamics. The JEPA-gated SSM primitive prevents collapse through separate state spaces while sharing the expensive dynamics (SSM + JEPA weights). Adding a new cognitive function costs ~1M parameters, not ~500M.

### 9.6 Why Self-Limiting Persistence?

Positive-only reinforcement creates immortal memories. The user keeps asking about WAL config — is it because it's important, or because the answer isn't sticking? The self-limiting mechanisms (diminishing returns, saturation detection, LLM-mediated signals, boost decay) ensure that retrieval-weighted persistence reflects genuine importance, not frustration loops.

# The Ponder Engine: A Hippocampal Memory Architecture for Artificial Intelligence

**A brain-inspired alternative to the context window that separates knowledge from processing, enables an artificial subconscious, and makes domain expertise a transferrable, composable resource.**

---

## 1. The Problem With How AI Remembers

Every major AI assistant operates on the same fundamental model: concatenate conversation history into a text buffer, feed it to a language model, truncate when the buffer overflows. This is the **context window** — a von Neumann architecture solution to a biological problem. Separate storage from processing. Copy data between them. Hope the buffer is big enough.

The brain never evolved this assumption. It stores patterns in the same neurons that process them. Retrieval is reactivation, not copying. Working memory is not a buffer — it's the subset of long-term memory currently activated by attention. And beneath conscious awareness, a **subconscious routing system** continuously decides where to look, what's relevant, what level of intelligence is needed, and whether conscious deliberation is even required.

We've built an architecture that mirrors this design. It's not a thinking machine. It's a **ponder engine** — the substrate that makes thinking possible by handling the questions every AI system faces but none currently answers well: *What do I know about this? Where should I look? What's important here? Am I the right intelligence for this task?*

---

## 2. The Three Memory Systems

Human memory is not one thing. It's at least three systems, each with different structure, different timescales, and different neural substrates. The architecture mirrors all three.

### Episodic Memory: What Happened

Episodic memory stores specific experiences — conversations, decisions, discoveries, frustrations. Each experience is encoded as an **episode**: one complete conversational exchange, stored with structured metadata about who was involved, what was discussed, how people felt, what was decided, and what happened next.

Episodes are linked into temporal chains by `follows` edges, forming the narrative structure of experience. They're stored with salience scores that predict future utility — a frustrating debugging session where a key decision was made is more important than a routine status update.

But episodes aren't the only thing that enters the system. Documents, emails, code files, web pages, audio recordings, and video all flow through the same ingestion pipeline. A PDF becomes hierarchical sections linked by `has_section` edges. An email thread preserves its reply chain structure. A code file's AST becomes a subgraph of functions, classes, and call relationships. An image is described by a vision model, its description encoded into triples, its raw bytes stored for future re-description when better models arrive. Everything becomes the same thing: structured triples in the graph, content in the store.

### Semantic Memory: What It Means

Semantic memory stores abstracted knowledge — facts, concepts, categories, and the relationships between them. It's produced by **consolidation**: a graph neural network periodically scans the episodic graph, identifies clusters of related experiences, and abstracts them into compressed semantic memories.

"WaveDB development with Alice (June 20-24): decided on HBTrie architecture, resolved WAL configuration, chose WaveDB over Postgres, achieved 2.6M reads/sec benchmark" — this is a semantic memory, abstracted from five separate episodes, stored as a single retrievable unit with links back to its source experiences.

The ontology — the class hierarchy that knows WaveDB IS-A Database and Frustrated IS-A AffectiveTone — is also semantic memory. It starts from a seed that includes both conversational categories and code structure types, ensuring the system allocates representational capacity for everything it might encounter. It evolves through discovery: when the system encounters a new category often enough, it promotes it. When a category stops appearing, it decays. The GNN periodically refines the hierarchy, predicting missing `subClassOf` edges and detecting misclassified entities.

### Procedural Memory: How To Do Things

Procedural memory stores sequences of actions — processes, rules, strategies. A code review process is a stored subgraph: read the diff, check for style violations, analyze security implications, summarize findings. Each step specifies what tool to use, what model size is needed, and what to do on failure.

Processes are learned through observation. When the system watches you perform the same multi-step task three times, it proposes a stored process. The fourth time, you say "review this" and it executes the process automatically, delegating individual steps to larger models when they exceed the current model's capability.

Meta-processes — strategy templates for handling novelty — sit above concrete processes. They don't specify exact steps. They specify decision points: "Can this task be broken into independent sub-tasks? If yes, apply parallel decomposition. If no, identify dependency order." These guide the model's reasoning without replacing it.

## 3. The Architecture

### Encoding: Experience Becomes Structure

Raw conversation enters the system. Two specialized models extract its structure:

**GLiNER2** (205M parameters, runs on CPU) extracts entities, topics, emotional tones, and decisions against an evolving schema. **GLiNER-Decoder** (205M parameters, also CPU) performs open discovery — it invents labels for entity types not yet in the schema, feeding the ontology's evolution. Together they handle the question "what's in this text?" — one with the stability of known categories, the other with the flexibility to discover new ones.

**Bonsai** (8B parameters, ternary weights, ~2.15 GB) extracts relations: who explained what, who decided what, what contradicts what, what follows what. These become triples in the graph. Bonsai also serves as query planner — converting natural language questions into structured graph queries — and as reality monitor, waking during consolidation to verify GNN-flagged anomalies with ternary {-1, 0, +1} judgments that can actively suppress incoherent patterns.

The content — the actual words, the raw bytes of images, the source code — is stored in a hierarchical key-value store called the HBTrie, analogous to the neocortex. The structure — the triples — is stored in a graph layer, analogous to the hippocampal index. The separation is the key insight: the graph stores sparse pointers that can reconstruct the full memory, just as the hippocampus stores compressed indices that reactivate neocortical patterns. A third index, a vector store, handles semantic similarity — the "what's similar to this?" queries that complement structured graph traversal.

### Retrieval: Pattern Completion

When a prompt arrives, the system doesn't load conversation history into a buffer. It treats the prompt as a **partial cue** and performs pattern completion via graph traversal.

"What was I frustrated about last week?" becomes a structured query: `tones=["frustrated"], temporal_filter="last_week", entity_mode="union"`. The ontology expander broadens the search — "frustrated" is a subclass of AffectiveTone, so episodes tagged with related emotional categories are also considered. The graph finds all episodes matching those constraints, scores them by relevance, and loads their content from the HBTrie. The activated set **is** the context. No separate buffer. No fixed token limit.

Temporal chain queries — "what happened after we implemented morphisms?" — follow `follows` edges forward from the anchor episode. Cross-domain queries traverse edges between domain graphs. Document queries return hierarchical sections with citation links. The retrieval mechanism is identical regardless of what's being retrieved.

### Consolidation: The Dream State

Periodically, offline, a graph neural network scans the entire memory graph. It scores every node and edge by structural salience — not just access frequency, but whether a node is a bridge between otherwise-disconnected clusters, whether an edge is the only path to a frequently-queried fact. It incorporates retrieval history: edges retrieved repeatedly over time have higher effective salience.

The GNN detects subgraphs ready for abstraction and collapses them into semantic memories. It predicts missing edges — implicit relationships that were never explicitly stated but are structurally implied. It detects anomalies — orphan decisions, temporal gaps, contradictions — and flags them for Bonsai verification.

This is the equivalent of sharp-wave ripple replay during sleep. The hippocampus replays compressed memories to gradually train the neocortex. The GNN replays the graph to gradually improve its structure.

### Forgetting: Self-Limiting Persistence

Nothing is ever deleted. But not everything persists equally. The forgetting system combines four mechanisms to ensure that memory persistence reflects genuine importance rather than accidental repetition:

**Retrieval-weighted persistence** means every time an edge is traversed in a retrieval, its decay rate drops slightly. The more the user asks about something, the harder it is to forget. But this boost has diminishing returns — the twentieth retrieval provides far less reinforcement than the first — and an absolute floor ensures nothing becomes immortal.

**Saturation detection** breaks the frustration loop. If the same edge is retrieved more than five times in twenty-four hours, the system stops boosting and may slightly increase decay. The user keeps asking because the answer isn't sticking, and the system stops reinforcing because the user keeps asking.

**LLM-mediated signals** let the language model annotate its own responses. `[IMPORTANT: this is a key architectural decision]` strengthens persistence. `[FRUSTRATION: user is stuck on this]` prevents reinforcement. `[CORRECTION: this fact has changed]` triggers reconsolidation of the old fact.

**Boost decay** means the persistence boost from a retrieval itself fades with a roughly seven-day half-life. A retrieval last month matters less than a retrieval yesterday. If the user stops asking, the edge gradually returns to baseline decay.

Facts that change are **reconsolidated**: the old version is marked as superseded with a validity end date, the new version is marked as current, and a `supersedes` edge links them. Default queries return only current facts. Historical queries — "what did I used to think?" — return the versioned history. And edges that survive three retrievals across fifteen or more days enter a late-phase state where their decay rate drops by an additional seventy percent — the architectural equivalent of a memory becoming independent of the hippocampus.

## 4. The Artificial Subconscious

The most novel component is not the memory systems. It's the **subconscious router** that sits between the user and everything else — and the unified cognitive primitive that makes it possible.

### The JEPA-Gated SSM: One Primitive, Many Minds

The architecture's previous design treated its neural components — the Mamba SSM for working memory, the JEPA predictor for salience, the gate for routing — as separate models with separate purposes. This had three consequences: proliferation of models (each new cognitive function required a new model), no unified dynamics (components were independent when they should be aspects of a single computational primitive), and missing cognitive functions (no uncertainty detection, no prospective memory, no self-model).

The revised architecture unifies these into a single primitive: the **JEPA-gated SSM**. It's composed of a shared Mamba SSM that maintains recurrent state, a shared JEPA predictor that performs predictive coding in embedding space, and a lightweight inhibitory gate that decides whether to excite or inhibit. The critical distinction is **shared weights, separate states.** The SSM and JEPA weights — about 480 million parameters, roughly 0.90 GB — are loaded once in GPU memory. Every cognitive function is an instance with its own state vector, its own gate, and its own input/output projections. Adding a new cognitive function costs about one million parameters, not five hundred million.

This maps directly onto the canonical cortical microcircuit — the same cell types, the same laminar structure, the same local connectivity repeated across the entire neocortex. What differs between regions is input sources, output targets, and inhibitory interneuron composition. The circuit is the same. The configuration makes it different.

### The Instances

Five instances of the primitive run continuously, each maintaining its own state and learning its own gating policy:

**The Retrieval Gate** is the subconscious router. It receives every prompt and the current working memory state. Before any retrieval happens, before any model generates a token, it predicts: which domain to query, which pathway to use, what meta-skills are required, what model size is needed, and whether conscious deliberation is necessary. All of this happens in milliseconds, below the threshold of anything the user or the LLM experiences.

**Working Memory** is the SSM instance that maintains continuous awareness. It's not a text buffer. It's a dynamical system whose current activation pattern is what the system is currently aware of. New inputs shift the state. Retrieved memories are injected as embeddings, not text. Old information decays gracefully rather than being truncated. The state dimension is fixed, but the information it represents expands and contracts dynamically.

**The Uncertainty Detector** knows when the system doesn't know. It flags three conditions: routing uncertainty (the Retrieval Gate wasn't confident about its domain prediction), novel entities (retrieved context contains entities not in the ontology), and unresolved contradictions (multiple sources disagree without resolution). These flags feed the EXPAND mechanism — loading more detail from the HBTrie — and the delegation ladder — routing to a larger model. The detector learns its thresholds from experience, calibrated by Oracle feedback during training.

**The Aspirational Model** operates in three temporal modes. In the present, it gates encoding strength — "I'm curious about this, encode it strongly." In the future, it maintains prospective memories — triggers that fire when conditions are met, like "alert me when you encounter information about Postgres performance." In the past, it weights retrieval persistence — every retrieval feeds back into the forgetting system, making frequently accessed memories more resistant to decay.

**The Self-Model** estimates the boundaries of its own knowledge. It learns when to say "I don't know" — not from hardcoded thresholds, but from experience. During training, the Oracle provides feedback: "You should have known this" or "You were right to admit uncertainty." The Self-Model's gate learns the difference.

### How the Subconscious Learns

Every routing decision produces an outcome. Did the user accept the response? Did the model have to delegate to a larger model mid-task? Was the response fast enough? Was expansion needed to retrieve missing details?

These outcomes feed back to the Retrieval Gate as reinforcement signals. Successful routes are reinforced. Routes that required unexpected delegation are penalized and re-evaluated. Routes that used a larger model than necessary get a small efficiency penalty.

Over time, the gate learns that "What is X?" needs a 1B model and no retrieval. "Why did X?" needs a 3B model and graph retrieval. "Review this for security" needs an 8B model executing a stored process that delegates security analysis to a 70B model. "Design a new X" needs a 70B model from the start.

The subconscious becomes personalized. It learns your domains, your patterns, your habits. It anticipates where to look before you finish asking. It knows which model size you need without you specifying. It gets faster and more automatic the more you use it.

### The Conscious/Subconscious Split

This maps directly to dual-process theory. System 1 — the subconscious — is fast, automatic, parallel, and handles routine queries without conscious intervention. System 2 — the conscious planner — is slow, deliberate, sequential, and engages when the subconscious can't resolve the route: when multiple domains conflict, when the task requires creative synthesis, when the confidence is low.

The user only sees System 2. System 1 is invisible — the pondering that happens before the response begins.

### Growing Up: Developmental Stages

The system doesn't emerge fully formed. Each component tracks its own maturation through four stages. In INFANT stage, the Oracle provides all training signal — the component learns by mimicking. In CHILD stage, the Oracle critiques the component's decisions rather than providing answers directly. In ADOLESCENT stage, the component self-regulates, consulting the Oracle only for edge cases. In ADULT stage, the component operates independently.

Transitions are gated by measurable metrics. The extraction models graduate from INFANT when their F1 score exceeds threshold on held-out data. The Retrieval Gate graduates when its routing accuracy matches the Oracle's decisions. The Self-Model graduates when its "I don't know" precision exceeds threshold. Each component matures at its own pace, and the system as a whole becomes more autonomous as its parts come online.

## 5. What This Enables for LLMs

### Any LLM Becomes a Memory-Augmented LLM

The architecture is a drop-in layer between the user and any language model. The LLM doesn't know about the memory system. It doesn't know about graph traversal. It doesn't know which domain it's in. It receives context and generates responses.

This means GPT-4 today, Claude tomorrow, a local model next week — the subconscious doesn't care. It provides the same context regardless of which LLM consumes it. The LLM is a plugin. The ponder engine is the platform.

### The Bidirectional Interface

The LLM can write back to the subconscious. Embedded in its response are memory commands — `[REMEMBER: this is important]`, `[LINK: Python, performance_issues, WaveDB]`, `[FORGET: the Postgres decision was superseded]`. These are stripped before the user sees the response and executed by the subconscious.

The LLM shapes its own memory. What it marks as important becomes more retrievable. What it links becomes connected. What it forgets becomes deprecated. And critically, the LLM's signals modulate the forgetting system — a `[FRUSTRATION]` tag prevents the persistence boost that would otherwise reinforce a memory the user is stuck on. Over time, the subconscious learns from these commands and starts making the same decisions automatically.

### Cost-Optimal Intelligence

Most real-world queries are factual recall or basic synthesis. A 1-3B model handles 80% of queries. An 8B model handles 15%. A 70B+ model handles 5%. The routing is learned, not hardcoded. The system uses exactly as much intelligence as the task requires.

A factual question doesn't wake the 70B model. A creative design task doesn't waste time on the 1B model. The cost scales with actual need, not worst-case need. A small model with perfect memory matches a large model without memory on the tasks people actually do most often.

### The Delegation Ladder

When a small model executing a stored process hits a step it can't handle, it delegates up. The process defines the delegation rules: "Step 2 (security analysis) requires a 70B model." The small model calls the larger model for that step, gets the result, and continues. The user never knows a larger model was invoked.

The small model becomes a conductor, not a soloist. It reads the score — the stored process — directs the musicians — the tools and larger models — and assembles the performance. It doesn't need to be smart. It needs to be good at following processes and knowing when to delegate.

## 7. Efficiency Gains

### Computational Efficiency

| Query Type | Traditional LLM | Ponder Engine |
|---|---|---|
| "What's the capital of France?" | 70B model, full inference | 1B model or SSM direct, <50ms |
| "What did Alice say last Tuesday?" | Can't answer (no memory) | Graph retrieval + 3B model, ~200ms |
| "Review this PR for security" | 70B model, full inference | 8B model executes stored process, delegates security step to 70B, ~2s |
| "Design a new sync mode" | 70B model, full inference | 70B model, full inference, ~5s |

The efficiency gain is not in making the hard tasks easier. It's in not using the hard-task machinery for the easy tasks. The 70B model sits idle 80% of the time. The 1-3B model handles the routine. The cost follows the actual cognitive demand.

### Storage Efficiency

A 70B-parameter model stores knowledge in its weights — roughly 140 GB of floating-point numbers that encode everything the model knows about the world. Adding knowledge requires fine-tuning or retraining. Removing knowledge is impossible. Sharing knowledge means sharing the entire model.

The ponder engine stores knowledge in graphs — structured triples that encode specific facts, episodes, and processes. A year of daily conversations might produce a few hundred megabytes of graph data. Adding knowledge is an insert operation. Removing knowledge is a deprecation edge. Sharing knowledge is exporting a WaveDB instance.

### Parameter Efficiency

The JEPA-gated SSM primitive dramatically reduces the architecture's footprint. The previous design required separate models for the SSM (~500M), JEPA (~300M), and gate functions — roughly 1.70 GB total for the mind layer. The unified primitive uses a shared backbone of ~480M parameters (~0.90 GB) plus five instance-specific gates and projections totaling ~5M parameters (~0.02 GB). Total mind layer: under 1 GB. The savings — nearly 0.8 GB — go directly to headroom for larger generation models or additional cognitive functions.

### Learning Efficiency

The subconscious learns from every interaction. Every routing decision that succeeds or fails updates the Retrieval Gate's weights. Every process that executes updates its success rate. Every anomaly that Bonsai verifies improves the GNN's anomaly detector. Every retrieval that the user values — or doesn't — shapes the forgetting system's persistence weights.

This is continuous, online learning. No retraining phase. No catastrophic forgetting. The system gets better at its specific job — routing your queries, retrieving your memories, executing your processes — with every interaction.

## 8. Scalability Across Distributed and Non-Homogeneous Hardware

### The Architecture Separates Knowledge From Processing

This is the architectural insight that makes distributed deployment natural. The processing models — GLiNER2, Bonsai, the JEPA-gated SSM backbone, the GNN — are small and identical across all instances. The knowledge — graphs, ontologies, processes — is what varies.

The entire processing layer fits on a single consumer GPU. The JEPA-gated SSM backbone uses ~0.90 GB. Bonsai uses ~2.15 GB. The GNN uses ~0.40 GB. The instance gates and states are negligible. Total VRAM: roughly 3.5 GB, leaving over 12 GB headroom on an RTX 5060 Ti. Total hardware cost: roughly $400-500 for the GPU, plus CPU and disk you already have. This is an edge-device architecture, not a datacenter one.

For the delegation ladder, larger models — 70B, 175B — run on cloud APIs. They're invoked only when needed, roughly 5-15% of queries. The cost is proportional to actual use, not worst-case provisioning.

### Linear Scaling

Adding a user means adding a set of domain graphs. The processing models are shared. A single GPU can serve multiple users if their queries don't overlap in time. Ten users with light usage share one GPU. A thousand users need a small cluster.

The scaling is linear in users, not quadratic in model size. This is the opposite of monolithic LLMs, where serving more users means replicating the entire 70B+ parameter model.
