## 2. The from‑the‑start solid approach

Ranked by pain caused vs. cheapness to design out upfront:

1. **Backbone objective mismatch (highest pain, cheapest to fix upfront).**  
   The original backbone was trained with a mean‑pool `z_k` objective, never on `flat_last`. The readout consumes `flat_last`, so the representation was never optimized for the readout’s input.  
   **Fix:** From day 1, include a `flat_last` query‑document relevance loss (e.g., margin loss or InfoNCE) on the real serve ring, **jointly** with the routing objective. The backbone then learns to produce a `flat_last` that is directly useful for relevance. No separate fine‑tune needed.

2. **Injection‑by‑meaning fidelity trap (high pain, trivial to design out).**  
   Re‑embedding `slot.text` instead of capturing the exact step‑input `u` caused a 20% fidelity break, which would have silently ruined any training.  
   **Fix:** The trace format must capture the exact step‑input embedding (`slots_step_input`) by construction. This is a one‑line schema change and costs nothing upfront.

3. **Class‑balanced loss weighting vs. sampling (moderate pain, easy to avoid).**  
   AdamW with per‑kind loss weighting collapsed training; class‑balanced sampling worked cleanly.  
   **Fix:** Always use class‑balanced sampling (inverse‑frequency, no replacement) for imbalanced relevance data. Never use loss weighting with AdamW for this problem.

4. **3‑seed variance‑luck trap (moderate pain, easy to avoid).**  
   Multiple 3‑seed passes gave false confidence.  
   **Fix:** The robustness bar is 6 seeds from the start. No decision is made on <6 seeds.

5. **Per‑kind bodies / MoE (moderate pain, avoidable by design).**  
   The selectivity gate requires a **single cross‑kind logit space**; any per‑kind decomposition makes logits incomparable.  
   **Fix:** Use exactly one shared readout head. Never split by kind.

**The right from‑scratch recipe:**  
- Train the backbone with a multi‑task loss: original ERAG routing (mean‑pool) + `flat_last` contrastive relevance loss on the serve ring.  
- Capture exact step‑input `u` in the trace format.  
- Train a single shared readout (e.g., cosine similarity with learned temperature) on top of the frozen backbone’s `flat_last`.  
- Validate with 6 seeds, class‑balanced sampling, no per‑kind bodies.

## 4. Fragility

**Overfit to 939 records:**  
Yes, moving 19.5M params on a tiny dataset risks overfitting. The fine‑tune used a low LR (1e‑5) and only 8 epochs, which limits memorization, but the resulting representation may not generalize far beyond the training distribution. The text‑bucket weakness is a symptom. Mitigation: validate on a held‑out set of sessions (you already did within‑corpus held‑out, which passed). Before full trust, test on a small out‑of‑distribution set if available.

**Throwaway readout capacity:**  
The throwaway readout (Linear→cosine) had low capacity, forcing the backbone to do the work. A different throwaway readout (e.g., a 2‑layer MLP) might have produced a slightly different backbone, but the core direction (query‑relevant `flat_last`) would be the same. The risk is that the backbone over‑adapted to the specific loss formulation (margin loss, hard‑neg mining). This is acceptable for a first working system; a from‑scratch joint training would remove this dependency.

**Truncated‑BPTT‑depth‑1 approximation:**  
Single‑step replay gradient is a biased estimate of the true multi‑step gradient because it ignores how the current step’s parameter update affects future states. However, for a **slot‑level relevance objective**, the dominant gradient flows through the step that produced that slot’s hidden state. Multi‑step dependencies are second‑order. The smooth loss drop (2.51→0.46) and the strong result confirm the bias is not harmful in practice. No need to quantify further unless you plan to train for many more epochs.

**Catastrophic forgetting of routing objective:**  
This is the **only fragility that could block shipping**. The shared `W_A`/`W_B` were moved. The original heads read through mean‑pool, which also uses those weights. The fine‑tune targeted an untrained path, but it still modified the shared parameters. You must measure the original metrics. If they hold, the fine‑tune is safe. If they drop, the fine‑tune is not usable as a drop‑in replacement.
